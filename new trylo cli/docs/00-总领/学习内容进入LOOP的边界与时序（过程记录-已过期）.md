## 现在还没有被决定的事

目前只明确四个产品意图：

1. Trylo 要同时支持用户学习和 Agent 学习；
2. 学习要真实改变后续执行，而不只是换 prompt 或调参数；
3. 学习不能把主 LOOP 变成高延迟、难恢复的大系统；
4. v0.3 的已有设计和实现可以进入讨论，但不能自动变成新 CLI 的核心合同。

除此之外，以下都尚未获批：`LearningDirective`、`TaskLearningPlan`、`MethodGuard`、四端口、八接点、固定优先级、100 ms/50 条批量阈值、P02-A/P02-B 拆法，以及“P05 不得改变 LOOP”等结论。它们可以作为设计素材和 spike 假设，不能被实现 Agent 当作需求。

## 真正需要讨论的问题

我们不是在讨论“要不要记忆”，而是在决定学习获得多大的运行时权力：

- 它只影响模型看到的上下文，还是能影响计划、工具路由和恢复方法？
- 学到的检查能否让一次执行回到 repair，还是只能在结束后给出建议？
- 用户刚刚纠正的内容是否在本轮立即生效？何时才成为跨任务规则？
- Agent 从失败中总结的方法由谁验证、谁晋升、谁撤回？
- LOOP 为归因需要记录到什么程度，才能既有证据又不背负学习存储？
- 学习系统不可用时，基础 Agent 是否无条件继续？哪些场景允许阻断？

这些问题没有拍板前，先写字段只会把答案藏进类型名里。

## 三个可选融合深度

### 候选 A：上下文增强 + 环外学习

LOOP 只在 dispatch 前获取一段已经筛选的学习上下文，执行完向外围发送结果摘要。所有抽取、判断、验证、晋升都在环外。

优点：最轻、最容易复用现有 runtime，也最容易关闭。  
缺点：本质仍接近 memory/prompt injection；无法可靠证明某条经验改变了工具选择或验证行为，特色较弱。

### 候选 B：薄学习控制面

这是旧稿提出、但尚未批准的方案。只有三类能力进入 LOOP：

1. **执行前的已生效影响**：把经过治理的用户约定、方法、事实或检查投影为本轮不可变输入；
2. **执行中的方法与归因**：在关键决策点允许已生效规则影响计划/工具/恢复，并记录“适用、采用、结果”的因果锚点；
3. **结束前的可验证影响**：部分已批准检查可以触发有界 repair 或诚实降级。

候选生成、用户画像、Episode 关联、模型复盘、A/B、效果归因、晋升/撤回、重型存储和 UI 全部留在外围。

优点：学习真正改变行为，不只是参数；热路径仍可保持很薄。  
缺点：必须认真定义学习规则的权力、优先级、不可用语义和归因证据；如果设计不好，会出现第二套权限系统或第二个调度器。

### 候选 C：在线学习型 LOOP

学习器在每次 model/tool iteration 后更新策略、候选或权重，并可能在同一任务中改变长期规则。

优点：适应最快，研究感最强。  
缺点：延迟、可重复性、恢复、隐私和调试成本最高；很难区分当前任务 working memory 与跨任务学习，也更容易让模型自评直接控制自己。

### 当前建议，但不是决定

我建议以候选 B 为主要讨论对象，同时吸收 A 的故障降级方式；不建议选 C 作为默认运行模式。原因不是技术洁癖，而是 B 是目前唯一同时满足“形成产品特色”和“LOOP 不变重”的中间点。

是否采用 B、B 中哪几项有控制权，必须继续逐项讨论。旧稿的具体接口只作为 B 的一份技术草图保留在本文件后半部分，不得直接施工。

## 候选 B 仍需逐项拍板的七个决策

| 决策 | 选项 | 对 LOOP 的影响 |
| --- | --- | --- |
| D1 生效载体 | 自然语言上下文 / 结构化规则 / 二者并存 | 决定是否只是 prompt，以及 provider-neutral 程度 |
| D2 可控制范围 | 只建议 / 可改变工具与步骤 / 可改变结束条件 | 决定学习的真实运行时权力 |
| D3 用户纠正 | 仅本轮 / 默认成为候选 / 明确同意才跨任务 | 决定用户学习的即时性与隐私边界 |
| D4 Agent 经验 | 自动候选 / 自动试用 / 自动晋升 | 决定验证成本与失控风险 |
| D5 学习检查 | 只提示 / 可触发 repair / 可阻断 final | 决定特色最强的一环是否进入 LOOP |
| D6 同轮适应 | 仅 working memory / 更新临时策略 / 更新长期资产 | 决定是否靠近候选 C |
| D7 证据粒度 | 任务摘要 / 关键决策事件 / 完整执行事件 | 决定归因能力、延迟和隐私成本 |

建议的讨论顺序是 D2 → D5 → D3 → D4 → D6 → D1 → D7。先决定学习“能做什么”，再决定类型和存储；反过来容易被现有实现牵着走。

## 用户学习与 Agent 学习不应被含糊合并

### 用户学习候选内容

- 用户明确要求长期保留的约定；
- 多次纠正形成的候选行为偏好；
- 项目范围内的稳定事实；
- 输出格式和验收方式；
- 用户对某次结果的明确反馈。

争议点：明确约定是否可立即 active；行为推断是否只能做候选；项目事实如何过期；不采集时是否仍允许应用旧偏好。

### Agent 学习候选内容

- 某类任务有效的方法步骤；
- provider/tool 的路由经验；
- 可恢复错误的 playbook；
- 可运行的验证 recipe；
- Team 的分工与并行策略。

争议点：谁证明方法有效；能否自动生成可执行内容；失败样本如何归因；模型/工具版本变化后是否自动失效。

即使二者最后共用一个运行时投影，也不意味着它们共用证据标准、晋升权限或保留策略。

## 不论选 A/B/C，都建议先守住的底线

这些是安全和工程底线，不等于已经选定学习架构：

- 学习不能授予工具、文件、网络、sandbox 或审批权限；
- 当前任务明确指令不能被历史推断静默覆盖；
- 原始模型自评不能直接晋升为长期规则；
- 学习不可用时，基础对话/工具 LOOP 应有明确降级路径；
- 用户要求不采集或删除时，不应借运行日志绕过；
- `completed` 与“经过某项验证”必须是两个事实；
- 所有跨任务生效内容必须能说明来源、作用域、版本与撤回状态；
- LOOP、UI 和学习存储不能同时成为同一状态的 writer。

## P00 现在可以做什么，不能做什么

P00 可以继续，不需要等待学习讨论完成，但只做真正无悔的地基：

- canonical attempt/action/tool/result/terminal 事件与因果 ID；
- 权限和审批由核心独立拥有；
- provider、tool、UI 通过 Trylo 自有协议适配；
- parity trace 能保留关键决策、工具结果、验证事实和终态；
- 模块边界允许以后插入策略输入和观察输出，但不命名为某个既定学习方案。

P00 明确不能：

- 创建 `LearningDirective`、`TaskLearningPlan`、`MethodGuard` 或四端口正式类型；
- 决定学习事件存储、批量阈值、generation/CAS、优先级和 repair 权力；
- 把 v0.3 的类型复制成新 CLI 合同；
- 让 P00 fixture 假装已经验证学习语义。

这样即使最终选择 A、B 或 C，P00 也不会白做；学习真正影响 LOOP 的代码要等决策记录批准。

## 学习决策 Sprint 与施工接点

施工顺序调整为：

```text
P00 无悔地基
  → L01 学习产品决策 Sprint（D1–D7）
  → P01 普通 Trylo Protocol + 被批准的最小学习合同
  → P02 Provider/Agent LOOP + 被批准的学习纵切
  → P03 真实工具、权限、验证
  → P04 会话与恢复
  → P05 v0.3 外围学习闭环
```

L01 在 P00 后立即开始，也可以在 P00 后半段用纯文档/throwaway spike 并行准备，但不得把未批准的 spike 代码带入生产。它的退出物不是“大架构文档”，而是七个逐项决策、两条端到端用户故事、一个失败/关闭路径，以及当时形成的 `ADR-L01-学习进入LOOP的最小权力（过程记录-已过期）.md`。该 ADR 已被当前顶层标准取代，不再具有现行规范效力。

P01 只冻结被批准的最小合同；P02 只实现一条学习纵切；P03 才用真实工具证明它是否比 prompt 注入更有价值。若实测证明价值不足或热路径过重，可以退回 A 或收窄 B，而不推倒 Provider/Tool/Protocol 核心。

## 候选 B 的技术草图（非规范、不可直接实施）

旧稿中的四端口可以作为讨论材料：

```text
InfluenceSource.prepare(task) -> InfluenceSnapshot | Baseline
DecisionPolicy.evaluate(snapshot, proposedAction, runState) -> Advice | Constraint
LearningObservationSink.append(attributionEvent) -> Accepted | Dropped
OutcomePolicy.evaluate(snapshot, artifacts, runState) -> Pass | Repair | Degraded
```

这里刻意换成中性名字，避免类型名先替我们决定产品语义。需要重点质疑：

- `DecisionPolicy` 是否真的要成为独立门，还是只参与 planner/context composition；
- `OutcomePolicy` 中哪些来源有权触发 repair，哪些只能提示；
- `LearningObservationSink` 是否需要独立于正常执行事件，还是由外围读取一份经过隐私过滤的投影；
- snapshot 是否必须整轮冻结，还是允许用户纠正在安全点更新；
- 这些能力能否只用 2–3 个接点完成，而不是旧稿的八个接点。

## v0.3 如何参与，而不是反向统治 LOOP

v0.3 先作为需求和实验库回答这些问题：

- 哪类用户学习在真实任务中产生了可观察收益？
- 哪类 Agent 经验能通过 checker/replay 证明，而非模型自评？
- 哪些字段只是存储实现细节，哪些是运行时不可缺的语义？
- 删除、撤回、跨项目作用域和失败经历分别要求什么证据？

只有被 L01 决策选中的语义进入 P01/P02。其余 v0.3 能力放在 P05 外围实现，通过 adapter 消费 Trylo 的运行事实。若 v0.3 实验发现新的高价值控制点，再提交 ADR 修改 LOOP；不能提前宣称 P05 永远不得改变 LOOP，也不能让 P05 任意反向耦合。

## L01 讨论必须拿出的两个端到端例子

1. **用户学习**：用户纠正 Trylo“修改此仓库前总要先运行指定检查”。下一次任务中，这条内容如何被发现、何时生效、是否改变行动、检查失败后发生什么、用户如何看见并撤回。
2. **Agent 学习**：Trylo 多次遇到同一类 provider/tool 失败并找到可靠恢复法。该经验如何成为候选、怎样验证、何时影响新任务、版本变化后怎样失效、错误归因怎样回滚。

任何方案若不能把这两条故事讲到可执行、可失败、可关闭、可撤回，就还没有资格进入 LOOP。

## 当前暂停点

在产品所有者批准 L01 前：

- P00 地基文档和 parity 工作可继续；
- Apache-2.0 分级准入和 provider/tool 候选评估可继续；
- 不开始学习核心类型、持久 journal、Method Guard 或学习驱动 repair 的生产实现；
- 旧稿所有具体字段与时序仅作为候选 B 的讨论材料。

这次真正要决定的不是“把多少学习代码塞进 LOOP”，而是：**学习在 Trylo 执行中拥有哪些不可替代、可证明有价值的权力；其余全部留在外围。**
