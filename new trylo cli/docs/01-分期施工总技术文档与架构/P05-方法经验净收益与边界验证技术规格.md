## 0. 结论

本阶段把“方法经验会被生成和再次注入”推进到一个可证伪的工程命题：

> 在限定任务族内，过去的真实经历形成的方法经验在未见任务中产生可核对的净收益；条件不成立时保持沉默；环境变化或反例出现后，旧方法能够退出适用范围。

它不是三层库继续堆字段，也不是把模型的 `helped=true` 当作效果。工程链必须完整覆盖：

```text
自然任务产生候选
  -> 编译时有选择身份和未选择原因
  -> Provider 确认 stream_start 后记录真实上场
  -> 同一次回答返回可归因的 helped bool
  -> 确定性任务结果独立记录
  -> 冻结组 / 反馈组比较
  -> 反例只产生更窄候选版本
  -> 成本门控在同预算下与“每次都学”比较
```

第一阶段不证明完整 Learning Agent，不验收用户深层学习、工具替换、统一第二调度器或 stable 表达。

## 2. 已验证工程基线

### 2.1 2026-09-22 本轮实测

| 检查 | 结果 | 含义 |
| --- | --- | --- |
| `npm run build` | PASS | 当前 TypeScript 可编译 |
| 方法/控制板关键测试 | 69/69 PASS | 方法生成、编译、持久档、M1 上场/反馈写口的局部合同稳定 |
| hermetic 全仓 | 1916 项：1908 pass / 3 fail / 5 skip | 三个失败均在 CLI 配置测试，受用户级 provider 配置污染；虽非学习缺陷，仍是全仓红门禁 |

红门禁对应 `cmd/trylo/main.test.ts` 的 doctor/config/openai-compatible 三例。施工前必须让这些测试隔离用户配置并重新取得全绿；不得通过修改期望值、跳过测试或清空用户配置来伪造 hermetic。

### 2.2 当前已存在的能力

- `MethodCard`、`AppliesWhen`、变体血缘、档案、双槽编译和字符预算已经存在。
- Board 已有持久 `MethodFielding` / `MethodFeedback` 类型、命令、事件、reducer、codec 与唯一写口。
- `recordUse` 能拒绝不存在的版本；`recordFeedback` 能拒绝无法对应真实上场的反馈。
- 同一 `(turnId, versionId)` 的上场计数去重，request 级明细仍保留。
- 方法槽不增加 provider 调用；关闭学习保持恒等路径。

### 2.3 当前承重缺口

1. `recordUse` 与 `recordFeedback` 只有测试调用，生产发送路径没有调用方。
2. `requestSlot` 只返回渲染后的 system message，所选 `versionId/proposalId/nicheId` 在 LOOP 边界丢失。
3. 当前 `requestSlotFor` 在内存里用 `beat` 增加 `uses`，这不是持久上场事实，重启后会被 Board 投影覆盖。
4. 没有方法反馈围栏；模型无法把某个 bool 精确对应到本请求真正展示的某个版本。
5. `AppliesWhen.labels` 只有在 hook 存在时才过滤；无 hook 会放行带标签的卡。`sameSession` 当前恒真。这两点必须先作为基线测量，不能先改代码再声称边界改善。
6. 当前没有机会/未上场原因、确定性任务结果、实验分组和成本曲线的统一输出。

## 4. 目标架构

```text
Method Board
  -> compileDecision(archive, context, budget)
       -> message
       -> selected receipts(version/proposal/niche/ref)
       -> bounded non-use reasons
  -> LOOP builds ProviderRequest(attemptId)
  -> first provider stream_start
       -> recordFielding(attemptId + selected receipt)
  -> response feedback fence(ref -> helped bool)
       -> visible answer stripped / invalid fence visible
  -> recordFeedback(exposureId + source event)

Canonical Board events -----------+
Deterministic task checker --------+--> isolated experiment projection
Usage / latency ------------------+       -> G0/G1/G2/G3 comparison
                                              -> continue / reject / undecided
```

实验投影是可删除的派生物；Board 日志和任务原始产物才是事实来源。

## 5. ME0：真实上场与反馈归因合同

### 5.1 槽交付不再只是一段文本

将 loop 与 learning 两侧的 `requestSlot` 返回值同步换成一个窄合同，名字可在施工评审中调整，但语义必须等价：

```ts
type MethodSlotReceipt = {
  readonly ref: string;       // 本请求内短引用，不是资产身份
  readonly versionId: string;
  readonly proposalId: string;
  readonly nicheId: string;
};

type MethodSlotDelivery = {
  readonly message: { readonly role: "system"; readonly content: string };
  readonly receipts: ReadonlyArray<MethodSlotReceipt>;
};
```

约束：

- `ref` 由 `turnId + beat + versionId` 确定性生成，不用随机数，不跨请求复用。
- Provider 只看到 `message`；receipts 只在执行侧内存流转，不进入 transcript、session、Desktop Protocol 或用户正文。
- 一条 message 中每个 hint 带对应短 ref，并附同一条短反馈说明；字符费用计入方法槽总预算。
- 无选中卡时仍可只有学习 intent；没有 message 时返回 `undefined`，关闭路径保持逐字节恒等。
- `compileDecision` 是选择的唯一实现；注入、诊断和实验都消费同一个决定，禁止复制第二套过滤算法。

### 5.2 真实发送边界

ProviderRequest 已有 `attemptId`。一条 receipt 只有在同一 attempt 收到第一条 `stream_start` 后才成为 `MethodFielding`：

```text
exposureId = hash("method-exposure", attemptId, versionId)
requestId  = attemptId
scope      = nicheId
```

发送语义：

- provider 在 `stream_start` 前抛错、取消或断开：不写 fielding；送达保持 unknown。
- 首个 `stream_start`：每个 selected receipt 写一条；同一 attempt 重放幂等。
- `stream_start` 后失败或取消：fielding 仍成立，因为模型已接受该请求；任务结果另记失败/取消。
- 记录失败只能产生结构化 degradation，不能让用户任务失败；错误不得静默吞掉。
- 不再在 `requestSlotFor` 中用 `beat` 假增持久 uses；排序读 Board 投影，当前请求内需要稳定排序时使用不可持久的局部已选集合。

### 5.3 方法反馈围栏

新反馈通道与 `trylo-learning` 提案通道分开，建议标记 `trylo-method-feedback`。只在本请求确有 receipts 时安装。

合法载荷最小形态：

```json
{"items":[{"ref":"m1","helped":true}]}
```

规则：

- 每个 ref 最多一次；未知 ref、重复 ref、非 bool、额外字段或超大小均判整块不可用。
- 合法围栏从可见回答和 transcript 中剥离；非法围栏原样可见并发 degraded 观察，沿用现有附加通道的 fail-visible 原则。
- 只有已写成功的 fielding 才能转成 `recordFeedback`；否则保持 unknown。
- `helped=false` 只是自报“不帮助”，不自动生成 counterexample，不触发删除、休眠或沉降。
- 缺少反馈不是 false；同一响应里的任务成功也不能自动补 true。
- 不新增 provider 调用，不要求用户逐卡确认。

## 6. ME1：隔离效果实验

### 6.1 四组

| 组 | 输入 | 状态变化 |
| --- | --- | --- |
| G0 无学习 | 当前任务正常上下文 | 无跨任务经验 |
| G1 只记忆 | 同来源最近原文片段，同字符帽 | 无归纳、无反馈改库 |
| G2 冻结检索 | 冻结方法库 + 当前选择器 | 记录结果但不改方法版本/排序状态 |
| G3 完整候选 | 与 G2 相同起始库 + 可归因反馈 + ME2 获准边界候选 | 只改各自隔离副本 |

四组必须固定模型、provider、工具版本、权限、任务初态、字符预算、重试额度和输出检查。运行顺序交错；测试批在计分结束前不得回流。

### 6.2 三个任务族

1. 结构化文件读取：格式变化、坏行、完整性要求。
2. 跨项目资料定位：workspace 边界、同名文件、版本差异。
3. 依据材料生成可核对变更清单：来源覆盖、字段准确、不得凭空补项。

每族先准备发现集，再准备未见正例和边界例。首轮目标按报告建议为每族 10/10/10；如果真实重复失败不足，允许缩为开发批，但不得用缩小后的样本宣称达到最终效果门。

### 6.3 结果记录

每次运行至少记录：

```text
runId / group / taskFamily / sourceTaskId / initialStateHash
model / provider / toolCatalogHash / permissionProfile
selectedVersionIds / nonUseReasons / exposureIds / helped values
deterministicCheckerResult / repeatedFailures / ineffectiveSteps
inputTokens / outputTokens / totalTokens / latencyMs
terminal / cancellation / unknown / environmentVersion
```

不得记录密钥、隐藏推理、无界用户正文或测试答案。产物引用使用 hash 和受控相对路径。

## 7. ME2：边界收窄候选

第一轮不直接扩 `MethodCard` schema。先在隔离实验中比较两个选择策略：

- 基线：当前 `compileSlot` 语义；无 hook 时标签不构成限制。
- 候选：卡声明某个条件时，缺少对应上下文证据视为 unknown 并不应用；反例只能生成更窄的新版本。

候选策略必须输出显式原因：`matched`、`state_ineligible`、`tool_mismatch`、`family_mismatch`、`label_unknown`、`label_mismatch`、`card_oversize`、`slot_budget`、`slot_count`。原因是派生诊断，不进入 MethodCard 权威内容。

如果现有 `tools/failureFamily/labels/sameSession` 无法表达真实边界，ME2 只能报告“表达能力不足”，不能用实验专用标签偷装长期产品语义。扩 schema 必须另写兼容 ADR，包含旧卡解码、canonical hash、niche 身份、迁移和回滚。

## 8. ME3：方法域成本门控

静态门控只回答本轮是否给方法子系统学习额度：

```text
collection off / budget exhausted -> idle
无新机会、一次性噪声、已有方法稳定解决 -> idle
重复未解且有预算 -> agent_method grant
```

它与“每个合格机会都放权、达到同一总预算即停止”比较。首轮学习增量费用帽为执行基线的 10%，实验重复执行另列预算；不 hold 当前任务，不新增学习确认问题。

通过 ME3 只证明方法域成本门控有效。至少两个子系统有真实机会、完成同预算比较、inter/offline 时钟和长期饥饿检查后，才可讨论统一第二调度器验收。

## 9. 指标、阈值与结论

### 9.1 主指标

- 每个合格任务的重复失败数和无效工具步骤。
- 未见正例首轮成功率。
- 边界误用率及其分母。
- 每次机会、上场、可观察行为、任务结果和反馈缺失率。
- 学习附加 token、延迟、维护成本和累计回本曲线。

### 9.2 试点阈值

- 边界误用率相对当前方法下降至少 50%。
- 未见正例首轮成功率下降不超过 5 个百分点。
- G3 对 G2 的重复失败相对减少至少 20%。
- 至少两个任务族方向一致。
- 预注册的后续 30 次适用机会内覆盖学习成本。

这些是试点决策阈值，不是论文常数。最终运行前用不计分开发批估计方差，然后冻结样本、最小改善、容忍界和停止点。

### 9.3 三种结论

- **继续**：改善幅度、边界、区间和回本同时过门。
- **否定当前机制**：反例可复现，或充分样本的改善上界低于最低价值，或预算到顶仍成本劣势。
- **未决**：机会不足或区间同时覆盖有益/有害；最多补一个预注册批次，不无限追显著性。

## 13. 迁移与回滚

- ME0 优先新增可选 delivery 元数据，不改变 ProviderRequest 公共形状和 Desktop Protocol。
- 若端口返回形状变化，loop 与 learning 两侧同一提交更新，合同测试阻止半迁移。
- 新 feedback 事件沿现有 Board 版本兼容规则解码；旧日志没有反馈即 unknown。
- 回滚 ME0 时停止安装 feedback channel 和 fielding callback；既有 fielding/feedback 事实保留，不删除历史。
- ME1/ME2 删除实验目录即可回滚，生产账 hash 必须保持不变。
- ME3 rollout 有单独开关；关闭后回到冻结检索/原静态 grant，不修改 Permission 或资产内容。

## 14. P0/P1 停止条件

- 全仓 hermetic 或 verify 仍红。
- 并行包正在改同一 method/loop 热文件而没有串行 owner。
- fielding 在 `stream_start` 前落账，或无法区分 sent/unknown。
- feedback 可以指向未展示版本、缺失被当 false、成功被补 true。
- 为实验建立第二本生产方法账，或让结果表反写生产状态。
- 学习路径扩大权限、安装工具、读取测试答案或记录隐藏推理。
- 为了表达实验边界静默扩 MethodCard schema。
- 测试未做红例注入，或只断言函数调用而没有验证外部事实。

## 15. 阶段退出

第一阶段只有在以下全部成立时退出：

1. ME0 真实发送—反馈—重启恢复链可复核。
2. G0–G3 隔离和冻结轨道可重复。
3. 至少两个任务族获得“继续”，或当前机制被明确否定；未决必须报告预算上限。
4. 负迁移、未知比例和成本曲线没有被总分隐藏。
5. 边界反例能使候选保持沉默或提出更窄版本，且没有扩大权限。
6. 全仓门禁绿，质量审计和交接证据齐全。

## 16. 明确非目标

- 不做 C3 用户 latent/Cognition/代表用户。
