## 1. 本轮回答什么

本轮不是再讨论“学习要不要进 Loop”，而是完成四块可独立验证、可并行施工的基础：

| 包 | 负责的系统 | 核心交付 |
| --- | --- | --- |
| WP-A | Execution Kernel | canonical contracts、可重放 reducer、执行纵切、干净质量基线 |
| WP-B | Learning Control Plane | 中央控制板、证据/提案/资产/激活、快照、恢复 |
| WP-C | Prompt/User/Skill/Workflow Learning | 提示词平权、用户学习、skill/workflow 候选与评测 |
| WP-D | Tool Learning / My Tools | 工具缺口、开源候选、隔离验证、换/改工具与贡献包 |

四包可以同一时刻开工，但不允许在同一个工作目录直接并发写。上一轮实际留下了“STATE 声称 17 条协议测试存在、当前源码已不存在，陈旧 dist 仍在执行”的证据；新的并行方式必须用独立 worktree，不能再靠“只写不同文件”赌不会互相覆盖。

## 2. 开工基线审计

### 2.1 已有、应保留

- TypeScript 5.8.3 + strict/noUnchecked/exact optional 等编译约束；
- Protocol 的 envelope、payload 上限、unknown kind、terminal immutability、sequencer、最小脱敏思路；
- 用户明确纠正 active、推断 candidate pending、withdraw/remove、collect=false 的最小行为；
- “学习不授予权限、当前指令不被历史推断覆盖、completed≠verified”的测试意图；
- P00 parity 合成轨迹和 `open/report` 七维研究结论；
- 核心不依赖 Desktop/UI/provider SDK 的方向。

### 2.2 不能当完成

- `domain/index.ts`、`loop/index.ts`、provider/tools/permission ports 与 CLI 仍是占位；
- 多份 Envelope/Fragment/ContextPort/JournalPort 违反单一 canonical contract；
- 当前 `npm test` 为 44 pass / 9 fail，失败来自陈旧 `dist` 与缺失 fixture；
- 清理 `dist` 后，名为 `protocol/test.ts` 的测试又不会被默认 glob 发现，存在另一种假绿；
- 文件 FragmentStore 没有多写者保护、CAS 或可恢复提交点；
- Context 降级会吞异常并丢输入 messages；
- Journal 还不是可供 Learning Loop 使用的有界、脱敏证据源；
- 当前没有真实 provider、tool runtime、permission state machine 或可运行 agent turn。

四包必须引用这些事实，不得复制旧 RUN 里的“全绿”结论作为当前证据。

## 3. 并行施工协议

### 3.1 强制隔离

协调者从同一个基准提交创建四个独立 worktree/branch。每个 worktree 使用独立 `node_modules`、`dist`、临时目录和端口；禁止四个 Agent 同时写 `D:\CC\trylo\new trylo cli` 这一份物理目录。

每包开工先记录：

- base commit；
- worktree 绝对路径；
- Node/npm/TypeScript 版本；
- 当前 `npm test` 的真实结果；
- 本包文件所有权；
- 本包加载的 `$trylo-code-quality` 版本/hash。

### 3.2 文件所有权

| 包 | 独占写范围 | 不得写 |
| --- | --- | --- |
| WP-A | `src/internal/{contract,protocol,domain,loop}/**`、共享 execution ports、`src/cmd/**`、build/test/quality scripts | knowledge/journal/learning/tool-learning 实现 |
| WP-B | `src/internal/{learning/control,learning/profile,knowledge,journal}/**`、学习存储 adapter、对应 fixtures | loop/domain/protocol、各领域候选算法 |
| WP-C | `src/internal/learning/domains/{user,prompt,skill,workflow}/**`、`src/internal/evaluation/**`、对应 fixtures | Control Board store/state writer、tools、permission、loop |
| WP-D | `src/internal/tooling/**`、`src/internal/learning/domains/tool/**`、My Tools read model、对应 fixtures | loop、Control Board writer、Permission Service、真实对外发布 |

`package.json`、`package-lock.json`、`tsconfig.json`、`AGENTS.md` 和架构文档只由 WP-A 或集成者改。B/C/D 如确需依赖，只写 dependency request ADR，不直接改 manifest。

### 3.3 跨包合同

施工期间只冻结语义和 fixtures，不从另一个尚未合并的 worktree import 源码。跨包对象为：

- `ExecutionProfileSnapshot`；
- `LearningObservation`；
- `LearningProposal`；
- `EvidenceBundle`；
- `LearningAssetVersion`；
- `ApprovalRequest`；
- `ActivationRecord`。

WP-B 是学习对象的 canonical 类型与状态 owner。WP-C/WP-D 输出各自领域的 draft/evidence，通过 adapter 转为 Board command；它们不得复制 Board lifecycle 或直接写 active pointer。WP-A 只定义 Execution Loop 需要的窄 Context/Profile port，不定义学习内部状态。

每包可以在自己的 worktree 编译测试；跨包接线只在集成阶段做。所谓“独立运行”是施工、测试和失败诊断不等待其他包，不表示四个提交可以任意顺序无冲突合并。

### 3.4 集成顺序

固定为：

```text
WP-A -> WP-B -> WP-C and WP-D (二者可任意顺序)
```

集成者只做合同映射、冲突解决和总测试，不借机增加第五套架构。若映射需要改变冻结语义，退回对应工作包修订，不在 glue code 中偷偷兼容。

## 4. 本轮公共行为合同

### 4.1 Execution Loop

- 明确 `Idle -> Turning -> Streaming -> Tooling/ApprovalWaiting -> Turning -> Terminal`；
- terminal 原因至少区分 completed/failed/cancelled/unknown；
- retry 是新 attempt，保留 correlation，不改写旧 attempt；
- completed 与 verification verdict 是两个事实；
- provider/tool/permission 都只经端口；
- 一次 task/turn 使用一个 immutable profile snapshot；
- Learning Loop 不可用不会阻塞当前执行。

### 4.2 Learning Loop

- 只消费已授权、脱敏、有因果引用的 observation；
- 领域 worker 只能提交 proposal/evidence；
- Board 是 lifecycle、active pointer 和 board sequence 的唯一 writer；
- 推断候选不能凭模型自评晋升；
- active 资产不可原地修改；
- 用户可查看、撤回、暂停、回滚和关闭采集；
- 学习失败不能伪装成空成功，Execution Loop 的降级结果必须可观测。

### 4.3 Tool learning

- Tool Curator 可以后台发现候选，不能自动下载/安装/切换/修改/发布；
- 候选代码先 quarantine，验证通过前不进生产工具搜索结果；
- learned/generated tool 以进程外本地 MCP/插件包交付，不注入 Trylo 核心进程；
- Permission Service 对每次副作用仍独立决策；
- “我的工具”是 Control Board/Tool Registry 的读模型，不是第二状态源。

## 5. 公共验证规则

### 5.1 干净测试

每个包必须证明测试发现不依赖陈旧 `dist`：

1. 在确认 worktree 绝对路径后，只清理该 worktree 的生成目录；
2. build + test；
3. 再次从干净生成目录 build + test；
4. 两次发现的测试清单和数量一致；
5. 修改/删除一个源测试后，陈旧编译测试不得继续执行；
6. 测试入口不能依赖运行时条件 import 测试文件。

### 5.2 质量顺序

每次自审固定顺序：可读性/维护性 → 架构 → 正确性 → 安全/权限/隐私 → 并发/恢复 → 性能/预算 → 许可证/供应链 → 测试/文档。

第一项失败即阻断。测试全绿不能覆盖双状态源、隐式控制流、吞错或只有作者能解释的代码。

### 5.3 禁止伪完成

下列任何一种结论都不算完成：

- “接口已经留好，逻辑以后补”；
- “用了 mock，所以真实失败语义不重要”；
- “测试很多”，但没有状态转移/反例/故障注入；
- 只贴最后一行通过，不记录命令、版本和完整摘要；
- 为通过测试删 fixture、放宽断言、吞异常或跳门禁；
- 从 `open/` 复制代码而没有 provenance、许可证和边界审计；
- 用 TODO 代替当前包明确要求的行为；
- 把已知红项移到“未来优化”后宣告完成。

## 6. 对 Grok 4.6 的统一执行约束

四份工作包都包含可复制提示词；以下要求同样强制：

1. 第一动作完整读取 `AGENTS.md`、`$trylo-code-quality`、双循环架构、本规格和自己的工作包；
2. 在写代码前创建 append-only `STATE.md`，写行为合同、边界、状态所有者、失败语义和验证矩阵；
3. 每完成一个 checkpoint 立即落 STATE、运行最窄测试，再继续，不允许一次性堆完后只做表面检查；
4. 遇到阻塞继续完成所有不受阻部分；只有精确列出 blocker、已尝试方法和所需输入后才可停；
5. 不以时长、token、文件数或测试数作为停机条件；只以 exit gate 为停机条件；
6. 不修改自己不拥有的文件；需要跨包变更时输出 integration request；
7. 结束前做两轮自审：作者审 + 反方审。反方审必须尝试证明设计有双写、假绿、越权或不可恢复；
8. RUN 记录精确命令、退出码、测试摘要、关键失败注入、diff 范围、许可证变化和回滚方法；
9. 最终只能写 `COMPLETE`、`BLOCKED` 或 `FAILED`，不能用“基本完成”“核心完成”；
10. `COMPLETE` 必须逐项引用 exit gate 证据。

## 8. 总退出标准

四包合并后，本轮只在以下全部满足时退出：

- canonical Envelope/Fragment/Profile/Proposal 等概念无重复生产类型；
- 干净 build/test 连跑两次一致，旧 `dist` 不会产生幽灵测试；
- 有一条 fake provider + fake tool + approval/deny + terminal 的可运行 Execution Loop；
- Learning Control Board 能从 observation 经 proposal/evidence 到 shadow/active/rollback 并崩溃恢复；
- 用户明确纠正能 next-boundary 生效，推断提示词提升只能先成为候选；
- skill/workflow 候选有独立 verifier 和回归证据；
- 工具候选能完成 discovery metadata → quarantine → verification → approval request → My Tools read model，未经授权不能越过 gate；
- collect=false、permission isolation、completed≠verified、unverified tool hidden 等反例全绿；
- 没有真实网络/外部发布副作用被测试或默认路径偷偷触发；
- 四包各有质量审计、状态记录、完整 RUN 和回滚说明；
- 集成审计不存在 P0/P1 finding。
