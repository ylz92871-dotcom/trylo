# D3 工具执行生命周期与权限/审批系统

## 0. 一页结论

- **终态数量差异是最大缺口来源**：各家工具终态从 2 态（aider/mini 无独立终态机）到 7 态（gemini `CoreToolCallStatus`）不等。Trylo `ToolOutcome` 仅 `result|error|unknown`，缺 `cancelled` 独立终态；gemini/codex 都把「取消」与「错误」分开，opencode 则把取消折叠进 `error`。
- **审批"过期"仅 codex 一家**：`ReviewDecision::TimedOut` 是唯一的审批侧超时终态（guardian 自动审阅超时）。goose 的 `expiry` 是"已记住授权"的 TTL（`permission_store.rs`），非 pending 审批计时。opencode/gemini/cline/aider 对 pending 审批**无计时器**（阻塞直到回复或作用域销毁）。Trylo `permission_expired` 目前只有 codex 同族。
- **args 维度权限**：gemini(`argsPattern`)、codex(prefix DSL)、opencode(`pattern`)、goose `ToolPermissionStore`(blake3 args hash) 都带参数维度；cline `ToolPolicy`/goose `PermissionManager` 是纯工具名布尔；Trylo `PermissionAction{toolCallId,name}` **无 args 字段**——与多数家的核心差距。
- **fail-closed 等价性**：Trylo `executeToolSafely/awaitPermissionDecision` 的 try/catch→unknown/failed 包装，语义等同 cline `requestToolApproval`（无回调→`approved:false`、抛错→`approved:false`）；缺的是 cline 的"无回调即拒"在 Trylo 里表现为 `request_failed` 而非默认 denied。
- **mcp InputRequiredResult 侵入 loop**：多轮往返（`resultType:"input_required"`）要求 loop 能挂起一个未完成工具并二次注入用户输入，与 Trylo 单进单出 `execute():Promise<ToolOutcome>` 模型冲突。

## 2. 参数校验归属与失败反馈

- **谁 parse**：opencode 用 Effect `Schema` decode；codex `serde_json::from_str`（`executed_tool_calls.rs:189`）+ registry `matches_kind` 校验 payload 种类；gemini `invocation.build()`；cline `parseToolArguments`（`agent-runtime.ts` 私有）；goose/aider/mini 无独立 schema 校验。
- **失败反馈给模型的形态**：
  - cline：`reason:"invalid_arguments"`，回填 `invalidInput:{rawInputText,parseError}`（`buildInvalidToolInput`），并入 `parseError` 文本。
  - codex：unknown tool→`FunctionCallError::RespondToModel(unsupported_tool_call_message)`；不兼容 payload→`tool {name} invoked with incompatible payload`。
  - mcp：`isError:true` 且 content 内放可纠错文本（Tool Execution Errors）；结构错误走 JSON-RPC error。
  - opencode：`tool-input-*` 事件期间 `ensureToolCall` 落 `pending`，最终 `tool-error`→`failToolCall` 写 `status:"error", error`。
- 结论：Trylo `ToolCallRequest.arguments:JsonObject` 假定已 parse 完成；`error{code,message}` 通道可承载 cline 式 `invalid_arguments`，但缺"原始文本+parseError"结构位。

## 3. 审批状态机（各家迁移表）

### 3.1 opencode（`permission/index.ts` + `v1/permission.ts`）

事件源 `Event.Asked`，回复 `ReplyBody.reply∈{once,always,reject}`+可选 `message`。

| 源状态 | 事件 | 目标 | 备注 |
|---|---|---|---|
| evaluate 命中 deny | ask() 内 | 立即 `DeniedError` | 不进 pending |
| evaluate 全 allow | ask() | 直接返回（不弹） | needsAsk=false |
| 无匹配/ask | ask() | Pending+`Deferred` | publish `Event.Asked` |
| Pending | reply=once | Resolved(succeed) | 仅放行本条 |
| Pending | reply=always | Resolved + 推 `approved[{permission,pattern,allow}]`，级联放行同 session 匹配 pending | |
| Pending | reply=reject(无message) | `RejectedError`，级联 reject 同 session 全部 pending | |
| Pending | reply=reject(带message) | `CorrectedError{feedback}` | |
| Pending | 作用域销毁 | addFinalizer 逐个 `RejectedError` | **无超时** |

- "always" 作用域：`approved` 存于 `InstanceState` 的 per-session 内存；`Approval{projectID,patterns}` schema 另存项目级（`core/src/permission/saved.ts`）。派生：`doom_loop`/`task` 用 `always:[name]` 或 `["*"]`。
- 修改参数再审：**无**（reject+feedback 是"纠错提示"非编辑回路）。

### 3.2 codex（`protocol.rs` ReviewDecision + `tools/sandboxing.rs` + `approvals.rs`）

| 源状态 | 事件 | 目标 | 缓存/持久化 |
|---|---|---|---|
| 请求 | Approved | 执行 | — |
| 请求 | ApprovedForSession | 执行 | `ApprovalStore` 进程内 per-session（`with_cached_approval`，key=序列化 `ApprovalCacheKey`） |
| 请求 | ApprovedExecpolicyAmendment | 执行 | `append_amendment_and_update` 写规则文件，跨 session |
| 请求 | ApprovedMcpPolicyAmendment | 普通工具视为错误 | MCP 专用，跨 session |
| 请求 | NetworkPolicyAmendment(allow/deny) | 记网络规则 | 持久化 |
| 请求 | Denied{rejection} | `ToolError::Rejected` | 无 |
| 请求 | TimedOut | guardian 自动审阅超时→`Rejected(timeout msg)` | **审批侧唯一超时** |
| 请求 | Abort | `CodexErr::TurnAborted` | — |

- 决策优先级（`prompt_is_rejected_by_policy`）：`Never`→冲突理由；`Granular` 按 `sandbox_approval/rules/…` 布尔把"该问的"直接变"拒"；`OnRequest/UnlessTrusted` 放行到问人。
- 审批缓存粒度：MCP 区分 `session_approval_key` 与 `persistent_approval_key`（`mcp_tool_call.rs:1445`），`apply_persistent` 视 `policy.allow_persistent`。

### 3.3 goose（`tool_execution.rs` + `permission.rs` + `config/permission.rs`）

Permission∈`{AlwaysAllow,AllowOnce,Cancel,DenyOnce,AlwaysDeny}`。

| 源状态 | 事件 | 目标 | 持久化 |
|---|---|---|---|
| ActionRequired 发出 | AllowOnce/AlwaysAllow | 派发执行 | AlwaysAllow→`update_permission_manager(name,PermissionLevel::AlwaysAllow)` 写 `permission.yaml` |
| ActionRequired 发出 | DenyOnce/Cancel | `CallToolResult::error(DECLINED_RESPONSE)` | — |
| ActionRequired 发出 | AlwaysDeny | 同上 + `PermissionLevel::NeverAllow` | 持久 |
| Pending(onshot rx) | 通道被 drop/cancel | `confirmation_rx.await` Err | — |

双层粒度：`PermissionManager`=纯工具名三态 `{AlwaysAllow,AskBefore,NeverAllow}` 持久；`ToolPermissionStore`=工具名+`context_hash(blake3(arguments))`+`expiry(Duration)` TTL 持久（**这是"记住授权"的过期，非审批等待计时**）。"always" 作用域：全局配置文件（跨 session/进程）。

### 3.4 gemini-cli（`scheduler/types.ts` + `confirmation.ts` + `message-bus.ts`）

`CoreToolCallStatus`：Validating→Scheduled→AwaitingApproval→Executing→{Success|Error|Cancelled}。`CompletedToolCall=Success|Cancelled|Error`。

| 源状态 | 事件(ToolConfirmationOutcome) | 目标 |
|---|---|---|
| AwaitingApproval | ProceedOnce | Executing |
| AwaitingApproval | ProceedAlways / ProceedAlwaysServer / ProceedAlwaysTool | Executing，session 内后续同类自动放行 |
| AwaitingApproval | ProceedAlwaysAndSave | Executing + `policy/config.ts` persistenceQueue 写 user/workspace 文件 |
| AwaitingApproval | ModifyWithEditor | **循环回 AwaitingApproval**（`resolveConfirmation` while-loop 重出确认） |
| AwaitingApproval | Cancel | Cancelled |

通道：`MessageBus(EventEmitter)`，`TOOL_CONFIRMATION_REQUEST`↔`TOOL_CONFIRMATION_RESPONSE` 按 `correlationId=randomUUID()` 匹配。`derive(subagent)` 产**非可信子总线**，剥离 `forcedDecision/serverName/toolAnnotations/details` 防伪造。"always" 三档作用域：session（Server/Tool/Always）vs persisted file（AndSave）。

### 3.5 cline（`agent-runtime.ts:prepareToolExecution`）

无独立审批状态机，是一条 skipReason 短路链：`inputParseError→provider-disabled→beforeTool hook skip→policy.enabled===false→policy.autoApprove===false→requestToolApproval`。审批结果仅 `ToolApprovalResult{approved,reason?}`。
- fail-closed：无 `requestToolApproval` 回调→`approved:false`；回调抛异常→catch→`approved:false`；拒因末尾拼 `TOOL_REJECTION_SUFFIX`。
- "always" 作用域：**运行时无"始终允许"回写**；`autoApprove` 来自 `tool-policies` 配置（`"*"`+per-tool），CLI 侧 `autoApproveAllRef` 仅进程内 toggle。
- 修改参数再审：**无**。

### 3.6 aider（`io.py:confirm_ask`）

无状态机，同步阻塞输入，返回 bool。响应集 `{yes,no,skip,all,don't}`。
- `(A)ll`/`(S)kip all`：`ConfirmGroup.preference`（本轮 shell 命令组内）；`explicit_yes_required=True` 时**禁用 (A)ll**（只认 y）。
- `(D)on't ask again`：写 `self.never_prompts` set（`(question,subject)` 键，进程内）。
- `--yes-always`（`self.yes=True`）对 shell/编辑因 `explicit_yes_required` 被强制成 "n"，即**封锁自动放行**。
- 过期/修改：**均无**。

### 3.7 mini-swe-agent

无审批。`LocalEnvironment.execute(action)` 直接 `subprocess(shell=True)`，`timeout` 默认 30s（`LocalEnvironmentConfig.timeout`），超时 `os.killpg(SIGKILL)`。

### 3.8 各家 pending-approval 计时器证据汇总（搜索 `timeout`/`expir`）

| 家 | pending 审批是否有超时 | 证据 |
|---|---|---|
| opencode | 否 | `Deferred.await` 直到 reply 或 finalizer（`permission/index.ts:101,54`）|
| codex | **是** | `ReviewDecision::TimedOut`（guardian 自动审阅）|
| goose | 否（有 grant-TTL） | `permission_store.rs` expiry 只作用于已记授权 |
| gemini | 否 | `awaitConfirmation` 无 timer（`confirmation.ts:63`）|
| cline | 否 | 回调 await 无 timer |
| aider | 否 | `input()` 阻塞，EOF→default |
| mini | 执行超时非审批 | `_run` timeout |

## 4. 执行中生命周期：进度 / timeout / cancel

**流式工具输出（streaming tool result）**：
- codex：`ExecCommandOutputDeltaEvent{call_id,stream,chunk:Vec<u8> base64}`（`protocol.rs:3581`），上限 `MAX_EXEC_OUTPUT_DELTAS_PER_CALL=10_000`。
- gemini：`ExecutingToolCall.liveOutput:ToolLiveOutput`+`OutputUpdateHandler(callId,chunk)`（`scheduler/types.ts:132,207`）。
- goose：`ToolStreamItem::{Message(ServerNotification),ActionRequired,Result}` 三路 merge（`tool_stream`），且流中可再发 ActionRequired（嵌套确认）。
- opencode：`session.updatePart`/`updatePartDelta` 把 running 态 part（含 content[]/structured）**增量落库**。
- cline/aider/mini：无 delta 流，结果整体返回。

**工具 timeout 默认值**：
- codex 执行：`DEFAULT_EXEC_COMMAND_TIMEOUT_MS=10_000`（exec.rs），`ExecExpiration{Timeout,DefaultTimeout,Cancellation,TimeoutOrCancellation}`，取消宽限 `50ms`。
- goose：`DEFAULT_EXTENSION_TIMEOUT=300`（config/extensions.rs），`GOOSE_DEFAULT_EXTENSION_TIMEOUT` 可覆盖。
- mini：`timeout=30`（LocalEnvironmentConfig）。
- opencode/gemini/cline/aider：工具层无统一默认 timeout（依赖 provider/abort）。

**cancel 后终态**：
- gemini：`Cancelled` **独立终态**（≠Error）。
- codex：`ExecExpirationOutcome::Cancelled` 与 `TimedOut` 分开；审批 `Abort`→`TurnAborted`。
- opencode：cleanup 把未完成 toolcall 置 `status:"error", error:"Tool execution aborted", interrupted:true`（**折叠进 error**）。
- cline：skipReason/error 路径，AbortSignal→error。
- goose：`Permission::Cancel`→declined error 结果。
- 结论：Trylo `ToolOutcome` 无 `cancelled`；`ToolPort.cancel()` 与 `cancelToolSafely` 存在但落 `unknown/error`，未表达"取消是正常终态"。

## 5. 结果回流与截断

**结果进下轮 provider 请求**：
- opencode：`tool-result`→`completeToolCall`，把 `{title,metadata,output,attachments}` 写进 ToolPart completed 态，`output` 为字符串回灌；`toolResultOutput` 决定结构化。
- codex：tool result 作为 `FunctionCallOutput` 类型 ResponseItem；`aggregated_output`/`raw_output`，带 `timed_out` 标记。
- gemini：`SuccessfulToolCall.response.responseParts:Part[]`（role 走 genai Part），`contentLength`/`outputFile`。
- goose：`add_tool_response_with_metadata`；拒绝时填 `DECLINED_RESPONSE`（含"DO NOT call again…STOP"强提示）。
- cline：tool result 与 tool call block 配对成一条 message（注释见 `tools.ts:89`）。
- aider：`run_shell_commands` 输出经二次 `confirm_ask("Add command output to the chat?")` 才作为 user 消息入 chat。

**截断常量（grep `truncat`/`max_output`/`MAX_…BYTES`）**：

| 家 | 常量/机制 | 值 |
|---|---|---|

| codex | `EXEC_OUTPUT_MAX_BYTES=DEFAULT_OUTPUT_BYTES_CAP`；`TruncationPolicy{Bytes,Tokens}` 中段截断 | 1MB |

## 6. 权限规则语法表达力对比（按强→弱）

| 排序 | 家 | 规则语法 | args 维度 | 与 Trylo `{toolCallId,name}` 差距 |
|---|---|---|---|---|
| 1 | gemini | TOML：`toolName`/`argsPattern`(regex)/`commandPrefix`/`commandRegex`/`decision`/`priority`(0-999,tier)/`modes`/`interactive`/`allowRedirection` | 正则匹配 args；`argsPattern.source` | 缺 args regex、priority tier、mode 条件 |
| 2 | codex | execpolicy prefix DSL：`add_prefix_rule(command_tokens,Decision)`；Decision `Allow/Prompt/Forbidden`；危险命令启发式 | 命令 token 前缀（args 的结构化子集） | 缺 prefix/token 匹配 |
| 3 | opencode | 通配符规则：`evaluate(permission,pattern,...)` `Wildcard.match` 双维（permission×pattern），`findLast` 覆盖 | pattern（如文件 glob、bash 命令模式） | 缺 pattern 维度（Trylo 仅 name） |
| 4 | goose | 双层：`PermissionManager` 工具名三态 + `ToolPermissionStore` `name+blake3(args)hash+TTL` | 第二层带 args hash | 缺 args-hash 记录与 TTL |
| 5 | cline | `ToolPolicy{enabled:autoApprove}` 布尔，`"*"` 通配工具名 | 无 | 布尔模型与 Trylo `needsApproval` 同构，无额外维度 |
| 6 | aider/mini | **无声明式规则**，仅当场 `confirm_ask`/直接执行 | 无 | 无规则可对齐 |

Trylo 现实：`PermissionAction` 只有 `{toolCallId,name}`，`readToolApprovalRequirement` 只有 `binding.needsApproval:bool`。表达力落在 cline(5) 与 aider(6) 之间，**缺 args 维度是全系最强差距**。

## 7. 副作用不可逆的分类层次

- **codex：sandbox 约束先于审批**。`SandboxPolicy{DangerFullAccess,ReadOnly{network},ExternalSandbox,WorkspaceWrite{writable_roots,network}}`、`SandboxMode{ReadOnly,WorkspaceWrite,DangerFullAccess}`、`NetworkAccess{Restricted,Enabled}`；`sandbox_override_for_first_attempt` 决定首个尝试是否绕沙箱，审批在沙箱失败后触发（on-failure 语义）。
- **gemini：解析失败即不信任**。shell parse 失败时（`policy-engine.ts:455`）：命中 DENY 立即执行拒；YOLO+`argsPattern` 强制 DENY；否则回落 `defaultDecision`（ASK_USER/非交互 DENY）。工作目录越界/非可信 git→强制 ASK_USER；重定向 ALLOW→ASK_USER 降级。`Kind` 标 `MUTATOR_KINDS`。
- **mcp：`destructiveHint` 等是弱提示**。`ToolAnnotations{readOnlyHint=false,destructiveHint=true,idempotentHint=false,openWorldHint}` 全部标注为 hints，"from untrusted servers 应视为不可信"；codex `ApprovalAction::McpToolCall` 携带 `destructive_hint/open_world_hint/read_only_hint` 进 guardian，goose `apply_tool_annotations(read_only_hint==false→AskBefore)` 消费。
- **opencode**：`edit/write/apply_patch` 归一到 `edit` permission，`disabled()` 里 deny 直接不注入；`snapshot` 前置于流，取消时 patch 记录。
- **Trylo 应在哪层表达（事实）**：`ToolBinding` 现无 `Kind`/`destructive`/`sandbox` 字段；`ToolOutcome` 无不可逆标记；缺 7 项中"不可逆分类"的任何承载位。

## 8. doom-loop / 重复调用防线

- **opencode**：`processor.ts:DOOM_LOOP_THRESHOLD=3`。`tool-call` 事件取最近 3 个 part，若同 tool+同 input(序列化相等) 连续三次→`permission.ask({permission:"doom_loop",patterns:[name],always:[name],ruleset:agent.permission})`，把重复变成需人批。
- **gemini**：`policy/config.ts`/`utils` 侧 `loopDetectedRef`（搜索命中 `loopDetected`），配合 plan-mode 阻断。
- **codex**：`tools/executed_tool_calls.rs` 记 `ExecutedToolCall` 证据进后续 prompt（**是 evidence 记录/去重提示，非硬性次数熔断**）；未搜到 `DOOM_LOOP` 类阈值。
- **goose/cline/aider/mini**：搜索 `repeat`/`doom`/`loop_detect` 未见等价熔断；cline 靠 `TOOL_REJECTION_SUFFIX` 抑制重试；aider 无。
- 结论：只有 opencode 有"重复 N 次→强制审批"的硬防线；gemini 有 loop 检测标志；Trylo 无。

## 9. Trylo 对照

### 9.1 工具终态

| Trylo `ToolOutcome` | opencode | codex | gemini | goose | cline | 各家"取消" |
|---|---|---|---|---|---|---|
| `result` | completed | Ok(ReviewDecision) | Success | Result(Ok) | tool output | gemini=Cancelled 独立 / codex=Cancelled 独立 / opencode=error+interrupted |
| `error{code,msg}` | error | ToolError::Rejected | Error | CallToolResult::error | skipReason/error | — |
| `unknown{code,msg}` | (abort finalizer Rejected) | CodexErr::TurnAborted | — | channel closed | approval throw | — |
| （缺 cancelled） | — | — | Cancelled | Cancel→declined | AbortSignal | 缺口 |

### 9.2 权限决议

| Trylo `PermissionResolution` | opencode | codex | gemini | goose | cline |
|---|---|---|---|---|---|
| approved | succeed/once/always | Approved/ApprovedForSession/Amendment | ProceedOnce/Always… | AllowOnce/AlwaysAllow | approved:true |
| denied | RejectedError/CorrectedError/DeniedError | Denied{rejection} | Cancel | DenyOnce/AlwaysDeny | approved:false |
| cancelled | RejectedError(finalizer) | Abort→TurnAborted | — | Cancel | AbortSignal |
| expired | **无对应** | **TimedOut** | **无** | **无(仅 grant-TTL)** | **无** |

Trylo 把 `denied/cancelled/expired` 分三态是领先的细粒度，但除 codex 外无家实现 `expired`，Trylo 需自带计时器才能兑现。

### 9.3 防御性包装等价性

- `tool-boundary.readToolApprovalRequirement`：snapshot 缺失→`required:true`（fail-closed），等价 cline `enabled!==false` 默认放行 + `autoApprove===false` 才问（注意方向相反：Trylo 缺 binding=需批，cline 缺 policy=放行）。
- `executeToolSafely`：catch→`unknown{code:tool_adapter_exception}`——把"适配器抛异常"归为不确定态而非 error，防误判成功；与 cline `requestToolApproval` catch→`approved:false`（把"审批失败"归为拒）同族，是**最接近 Trylo 的 fail-closed 参照**。
- `awaitPermissionDecision`：`ticket.toolCallId!==action.toolCallId`→`permission_ticket_tool_mismatch`——校验票据绑定，等价 gemini `correlationId` 匹配、goose `(session_id,request_id)` oneshot key、cline `toolCallId` 相关。

## 10. Trylo 缺口

1. `PermissionAction` 缺 **args/pattern 维度**（全系 gemini/codex/opencode/goose-store 都有；Trylo 仅 `{toolCallId,name}`）。
2. `ToolOutcome` 缺 **cancelled 独立终态**（gemini/codex 均单列）。
3. `permission_expired` 无行业通用实现可抄——仅 codex `ReviewDecision::TimedOut` 同类，需 Trylo 自定计时策略并文档化。
4. `ToolBinding` 缺 **副作用分类**（`Kind`/`readOnly`/`destructiveHint`/sandbox 需求）——影响"先沙箱后审批"或"只读免批"编排。
5. 无**工具级 timeout 默认值**（codex 10s / goose 300s / mini 30s 三家给数，Trylo `execute` 仅收 `AbortSignal`）。
6. 无**输出截断策略位**（opencode 50KB/2000 行落盘、codex 1MB 中截、gemini 2000/2000/20MB）。
7. `ToolPort.snapshot()` 缺"**deny→从 provider 请求移除**"语义（opencode `visibleTools`）与**命名空间前缀**（`mcp__` / `discovered_tool_`）。
8. 无 **doom-loop / 重复调用防线**（仅 opencode 有硬阈值）。
9. `PermissionResolution.approved` 无 **"always"作用域层级**（session vs persisted file）与 codex 式 **amendment 回写**、gemini 式 **ModifyWithEditor 编辑回路**。
10. `request()` 无回调/无绑定时的默认方向需明确：Trylo 现走 `request_failed`→`permission_unavailable`（`reduce-permission-failure.ts`），而 cline 走 `approved:false`（denied）——两者语义应二选一并统一。
11. mcp **InputRequiredResult 多轮往返**无法被 `execute():Promise<ToolOutcome>` 单进单出模型表达，需 loop 支持"未完成挂起+二次注入"。
