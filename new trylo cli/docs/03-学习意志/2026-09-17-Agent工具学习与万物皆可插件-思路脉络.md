> 上游：文件名称基于用户本次思路；具体内涵与 red-line 对齐见下。施工包（02-分期工程产出）必须服从本脉络；UI 部分属 desktop 后续跟随，现在**不做**（见 §3 挂账）。

## 1. 核心主张（产品所有者原话整理）

- 决定 Agent 水平的，可能既不是提示词、也不是 skills，而**是工具——那些外置的插件**。
- 第一层：现在的 Agent 学习产生 skills，本质是**模仿人类经验获取**，属于"还算好用"的部分。
- 第二层（新增方向）：**像人那样主动反思"工具不好用"**，给 Agent 提供**更换工具的权力**：
  - ① 主动思考现有工具不足/缺失 → **换工具**：做一个提示，让 Agent 去开源平台选最合适的工具。（不做自有插件市场——个人开发者做不了，但不影响 Agent 去开源平台取。）
  - ② 更深一层：Agent 发现"最好的工具也不合适" → **自己升级工具**。
- 提供「**我的工具**」给用户：放大 Agent 自己换来的、或 Agent 自己升级的工具。
- **工具升级成本更高 → 换工具、升级工具都要问用户授权。**
- 用 **subAgent** 去完成换/升级这件事，**不影响主 Agent 的工作**。
- 取来的工具必须是**开源、可修改**的；鼓励用户向原开源工具**提交自己的升级**（作为"我的工具"里的选项）：
  - 直接下载的 → 不带标识；
  - 优化过的 → 带**优化标识**；
  - 优化标识设一个**提交按键** → 生成一段提示词，让 Agent 帮他们提交优化的工具、做开源贡献。
- 第三：现在已有的部分工具（除内置）走 **MCP**，打包成专用工具、走本地（因为要可修改），现状还不用太思考，看用户选不选择下载。
- 后面会提供更多可修改的工具；**接插件的接口一定要弄好**，方便 Agent 换自己的工具；并提供一个**制作插件的选项**，帮用户自己造插件。

## 2. 与总领红线的对齐（作为本次讨论的共识固化）

- 换工具、升级工具、向开源提交——都是**显式授权**动作（用户原话「要问用户授权」，且更新/提交由用户决定）。与总领「未审批的下载/安装/切换/修改工具与对外提交必须走显式授权」「学习只能提案，权限/安装/贡献永远人审」一致。
- 学习不扩张权限：Agent 只能**提议**换/升级工具，审批与发布权永远在用户。

## 3. 【UI 挂账】desktop 后续随此改变的部分（当前不做，现只标记）

> desktop 会跟着本方向改 UI。下列 UI 是这次思路**缺的/将出现的**，属桌面侧以后跟随的范围，现不需要实现，只在此挂账，避免丢失。

- **「我的工具」面板**：列出 Agent 换来/升级的工具与内置工具；区分**来源/优化标识**（默认下载无标 / 优化过的带优化标识）。
- **优化标识 + 提交按键 UI**：对「优化过的工具」显示该标识与一个「提交开源贡献」按钮；点击后**生成一段提示词（让 Agent 帮用户起草/准备开源贡献）**，再由用户发布。
- **换/升级工具的授权确认 UI**：Agent 提议更换或升级某个工具时，给用户的确认/授权交互（含"换哪一个、为什么、来源开源地址"等）。
- **subAgent 进展展示**：换/升级在后台做时，向用户展示进度、不阻塞主对话。
- **插件制作向导 UI**：面向用户的「制作插件」引导（用已有 builder/package-spi/mcp-runtime 能力）。
- **MCP 专用工具（走本地、可修改）的下载/选择 UI**：用户选择是否下载当前提供的包。

> 以上仅标记，desktop 当前不动。CLI 侧相关（tooling/ 已有的获取/审批/我的工具/贡献/隔离/沙箱及此方向的设计）走 02-分期工程产出，不落此处。

## 4. 2026-09-17 第二轮确认（所有者逐条拍板）

> 本节按所有者原话整理。**【调研】** 标记的条目来自 `open/report/` 调研结论，不是所有者原话，仅作依据引用，所有者可推翻。

**【所有者】** ⑧ UI：先标记、现在不管。

**【调研】** 以下为调研结论（来源 `open/report/tool/00-SYNTHESIS-tool-learning-2026-09-17.md`），作为本方向技术方案的依据，非所有者原话：
