## 方法与范围

本轮做了六轮反例驱动审计：每轮选择新的故障轴，对保留的未修实现运行反例，再修改或确认已有改造并复验。第五轮确实在前四轮修复后继续找到新问题；第六轮新反例确认了第三轮改造对二进制管道的修复。各轮由同一执行者自审及自动探针完成，不冒称多个独立审计者。

修改仍在新版 CLI 的工具适配层与共享 UTF-8 裁切机械层。权限、会话 owner、真实模型配置、Desktop、旧 CLI、浏览器与 Windows MCP 未修改。本轮不创建子代理，不对正在运行的客户端热替换，也不把 hermetic 测试视作真实模型任务成功率。

证据根目录：`evidence/2026-10-22-builtin-tool-adversarial-v2/`。探针与独立构建保存在 `work/builtin-tool-quality-20261022/adversarial-v2/`。

## 第一轮：字节、行数与 Unicode 组合攻击

对 V1 的 `truncateOutput` 测试 1,260 个组合，覆盖 0/1/4/7/8 等小字节上限、0/1/2 等行上限、中文、emoji、混合文字与大量换行。**852 个组合**触发字节越界、行数越界、拆开代理对或负数丢失量中的至少一项，见 `round1-baseline.json`。

修复：小预算严格执行，不再为提示文字突破预算；行数裁切也受字节预算约束；共享 `cutTailToBytes` 从字符边界保留尾部，替代以 UTF-16 长度猜测 UTF-8 尾部。修复后同组 1,260 项探针无异常，见 `round1-green.json`。新增回归测试针对未修构建出现预期失败，见 `round1-red.log`。

## 第二轮：工作区别名与读取取消竞态

以真实目录 junction/symlink 作为工作区，攻击 read/list/search/glob/find 的路径一致性与 `.gitignore`。未修搜索返回带 `../` 的物理路径，还会导致忽略规则不生效。另一个注入 reader 在返回内容的同一时刻发出取消，旧 `read_file` 仍返回成功。两条反例在修复前均失败，见 `round2-red.log`。

修复：ToolPort 创建时统一物理命名空间，同时保留调用者的绝对词法别名；不放宽工作区或链接 containment。`read_file` 在 reader 返回后再次检查取消。新反例加已有中文/ignore/定位测试 **7/7 通过**，包括默认 `ADMINI~1` 临时目录环境，见 `round2-green.log`。V1 留下的导航别名问题已在本轮修复。

## 第三轮：启动前取消与持续日志内存

预先取消 spawner，再请求能写入 marker 文件的命令。旧实现仍启动并写文件，然后把 `aborted: true` 当作取消事实；真正副作用已经发生。原始失败见 `round3-red.log`。修复后 spawner 在环境取得前后拒绝已取消请求，并在装上取消监听后补查信号；单进程和管道均不得启动。

持续日志探针让子进程输出 **96 MiB**，工具输出上限只有 **4 KiB**。旧实现先把全部 stdout 存入数组再裁切，父进程堆增长 **217,607,952 字节**，约 207.5 MiB。新 `OutputCapture` 在收集过程中只保留有界的头尾片段；管道的中间 stdout 直接传给下一段，不再另外复制保存，stderr 共享一份有界捕获。相同探针父进程堆增长 **4,347,560 字节**，约 4.1 MiB；输出仍为 4 KiB，并保留 `TAIL-END`。原始数值见 `round3-memory-baseline.json` / `round3-memory-green.json`。这是本机探针的 JS 堆测量，不是整个系统 RSS 或所有程序的内存保证。

新增捕获单元测试验证 2,000 次混合 Unicode 写入后存储仍不超过 4 KiB、字节计数正确、尾部错误保留。单进程/管道/平台提示相邻回归最终 **34/34 通过**，见 `round3-green-normalized.log`。首轮其中两个已有 cwd 断言受系统短路径影响，保留在 `round3-green.log`；使用真实、仓库外、CommonJS 的长路径临时目录复跑，没有改动这些断言。

## 第四轮：新样本与反馈语义

使用新固定种子 `0x7ab91d` 生成 **4,000 个新组合**，再查字节/行上限、Unicode 与丢失量一致性；无新的算术越界。另查人可见反馈发现：仅因行数裁切而丢失 451 字节时，提示却写着“0 bytes omitted”。见 `round4-baseline.json`。

修复：行数损失只报告其实际可知的行损失，不复用字节裁切阶段的零值；如果提示本身放不进上限，保留有界内容及 typed `truncated`，不为提示再突破预算。新样本保持 **4,000/4,000**，语义反例也通过，见 `round4-green.json`。

## 第五轮：十进制位宽边界

继续针对裁切标记的数值与结构化字段相等性攻击，遍历原始长度 40–1199 与五种预算，**5,800 个组合中 790 个**发现提示数字与实际 `omittedBytes` 相差。原因是先为长数字预留字节，最终较短数字又缩短提示，从而改变提示所声明的损失。见 `round5-baseline.json`。

修复：为数字字段保留固定宽度，数值缩短时以空格补足，不用前导零。提示与结构化数值都依据同一个实际返回长度。新回归对未修第四轮模块运行时失败，见 `round5-red.log`；修复后 **5,800/5,800** 探针和 **16/16** 输出相关测试通过，见 `round5-green.json` / `round5-green.log`。

## 第六轮：退出码为零的二进制管道损坏

以真实 producer 输出 `ff 00 c3 28` 四个字节，consumer 收齐原始字节后输出 hex。V1 返回 `efbfbd00efbfbd28`，退出码仍为 0；其日志 collector 对管道中间 stdout 设置了 UTF-8 文本解码，把非法 UTF-8 字节替换掉。第三轮改造不再观察/解码中间 stdout，当前实现准确返回 `ff00c328`。见 `round6-baseline.json` / `round6-green.json` 与归档重放探针。这证明退出码与字节完整性必须分别检查；没有把 stdout 最终文本解码误称为任意二进制文件输出能力。

## 合同与可维护性复核

- 工具名称、参数 schema、权限决策、退出码/超时/取消分类均保持现有 owner。修复后的反馈更严格，既有“提示允许少量超预算”的容忍不再适用。
- `omittedBytes` 保留原有兼容定义：源字节数减实际返回文本字节数。内存捕获提示另报 `bytes produced`，不把片段长度当成完整日志量。
- 新增 `OutputCapture` 只负责流捕获，存储由一处持有；stdout 与 stderr 各有一份上限。保留量 getter 和真实外部探针配合验证，未靠自报 `completed` 判通过。
- `cutTailToBytes` 是共享协议机械 helper，没有环境读取、进程状态或权限语义；输入输出仍为字符串。
- 无新增依赖、锁文件或许可证义务。没有自动重跑副作用，没有跳过拒权或恢复合同。
- 新旧注入 reader 继续可用；工作区别名规范化保留原 alias，绝对 alias 读取与原 containment 回归一起检查。

## 最终检查

完整质量检查首轮 10/11 项通过，仅一条真实 PNG 引用用例失败，见 `verify.log` / `verify-initial-result.json`。这是本轮别名统一引入的兼容回归：普通物理根也被标成了 alias，导致图片引用从相对路径变成绝对路径。修复为仅在词法根与物理根确实不同时自动增加 alias，保留调用者明确提供的 alias。

随后在系统 `ADMINI~1` 环境扩大复验，发现图片测试夹具自身也是实际短路径别名。普通工作区图片测试的夹具现在显式取得物理根，原相对引用断言不变；真实 junction 的测试新增图片引用必须固定到物理文件的断言。两种合同分开验证，最终中文/ignore/别名/图片 **11/11 通过**，见 `alias-compat-final-green.log`。中间的未通过记录 `alias-compat-green.log` 同样保留，没有把源码回归归因于环境后跳过。

Windows PowerShell here-string、引号与中文 stdin 通过当前源码独立编译后 **2/2 平台检查**，见 `windows-build.log` / `windows-unicode-platform.log`。

最新候选 ToolPort 的真实 Windows 串联冒烟再次通过：读/改/磁盘读回、长行/二进制/大文件搜索、连续命令 stdout/stderr、后台管道零启动与单进程中文 stdin/轮询/停止，见 `windows-tool-smoke.json`。

第二次完整复跑的 `verify-rerun.log` 出现原生 `VirtualAlloc failed`，伴随 host-filesystem 进程失败、PowerShell/native 与 batch/PATH 用例失败；该日志未产生完整结束报告，不计通过。保留资源预检 `resource-retry-preflight.json`。在不改产品代码或断言的情况下，将涉及的三组用例单独以进程并发 1 复验，**16/16 通过**，见 `resource-failures-rerun.log`。随后再次按原始完整门禁命令（默认并发配置）重跑，结果单列在 `verify-resource-retry.log`，不覆盖前两次失败。

## 仍未收口

1. `read_file` 的整文件读取再选行方式尚未改为流式按行读取；大文件输入内存问题不能用本轮 shell 日志修复替代。
2. JavaScript regex 仍共用调用线程，极端复杂正则需要独立 CPU/时间隔离；1 MiB 单文件上限不能证明正则计算时间有界。
3. 本轮内存数据针对普通前台进程及管道捕获；后台/PTY 仍由原 registry/helper 管理，不能将结果外推成所有终端路径的内存验收。
4. 浏览器和 Windows MCP 工具尚未进入这组修改。未重跑真实模型长任务、原生 Desktop、安装包或设备验收。
