## 故障与合同

本次没有把所有现象归为同一种权限问题，沿实际消费者分别核查：

1. **图片丢失已证实。** MCP stdio 与 HTTP 的结果解释原来只调用 `extractText`，成功结果中的 image 内容被丢弃。模型收到成功文字但没有图片，只能尝试文件复制等迂回操作。这是协议到运行时交付遗漏。
2. **辅助程序重复设置标签已实机复现。** 用户所报缓存可执行文件已经具有 Medium / NoWriteUp 标签。原保护脚本在同一受限环境中再次写标签失败；修复脚本只读校验现有正确标签，成功且原程序 SHA256 未变。该证据不证明所有 Windows 权限环境均已修复。
3. **截图缓存处理有缺口。** 原 Python 路径只处理独占创建的 FileExistsError，不能处理 Windows 上已有不可写文件可能返回的 PermissionError；可选原图预览缓存的 I/O 故障还会使整个截图失败。此分支由权限失败注入和缓存完整性测试证明，未把用户日志中那个已过期缓存文件的具体 ACL 猜测写成事实。

保持既有 Permission Service、MCP 审批、Windows 隔离和模型图片能力边界。没有授予 Everyone 写权限、修改整个 AppData ACL、停用沙箱或改全局 provider。

## 实现与兼容

- `McpToolOutcome.inlineImages` 是传输侧暂存的可选字段；纯文字结果形状保持原样。stdio / HTTP 共用解析与体积上限检查，不把二进制塞入文字结果。
- MCP 执行适配器把经过格式、大小、MIME 校验的图片按摘要写到工作区 `.trylo/tmp/mcp-images/`；采用既有工作区路径守卫、独占创建与已有文件摘要校验，不接受服务端提供的任意本地路径。已有文件遭篡改或缓存跳转到工作区外时失败。
- 在返回 `ToolOutcome` 前移除传输字节，只交付既有 `ImageReference`。Execution Loop 和 durable journal 无须新增图片格式；既有 provider 包装层重新校验文件摘要后附上图片。取消、无法交付、错误图片均是可见终态，不能把没有图片交付说成成功。
- 成功结果明确说明图片已经附上，无须复制缓存或重复截图。
- Windows 辅助程序先用 `LABEL_SECURITY_INFORMATION` 读取独立于本地化名称的完整性标签，仅在标签不符合要求时尝试原有设置操作。DACL、可信所有者、重解析点和摘要检查保持原逻辑；真实设置失败仍中止。
- Windows-MCP 本地维护分支复用完全匹配的不可变原图缓存；缓存 I/O 失败时保留内联截图并显示原图预览不可用的说明。缓存摘要不匹配不会被当作可复用。

没有新增第三方依赖。图片数据的唯一写入者是 MCP 运行时交付适配器；权限仍由既有权限服务决定。
