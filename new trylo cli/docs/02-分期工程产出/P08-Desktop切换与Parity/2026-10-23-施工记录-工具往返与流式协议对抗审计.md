## 行为合同与确定修复

工具结果必须进入后续模型请求，最终答案交付一次；供应商结束元数据独立于正文存在。工具参数只按真实 call_id 开放和结算，最终快照可补回缺失片段但不能重复执行。思考 token 是输出 token 的子集，统计不可漏记或相加两次。空响应必须失败，不能制造完成。所有变化在供应商适配层，核心循环、权限所有者、学习控制面和 CLI v1 事件格式未扩展。

| 反例 | 修复前实际表现 | 本轮处理 |
| --- | --- | --- |
| Chat 结束帧 delta=null / 缺失 | 丢失 finish，执行工具后终态 unknown，原生续接未捕获 | 无正文仍处理结束元数据 |
| Chat 带工具调用却标为 stop | 执行工具后直接 completed，模型没收到结果，无最终答复 | 以已收齐工具调用事实要求后续请求，同时保留原生捕获 |
| Responses item_id 与 call_id 不同 | 残留一个未闭合工具参数块 | 按 item_id 装配，只在确认 call_id 后开放公开参数块；稀疏流先私存片段 |
| Responses usage 嵌套详情 | reasoning/cache 一律记成 0 | 保留 reasoning_tokens/cached_tokens，output 和 total 不重复加思考 |
| 碎片参数损坏、结束快照有效 | 忽略有效最终参数 | 最终完整参数为准，同一 item 仅结算一次 |
| 仅 completed.output 携带工具调用 | 丢失调用并空完成 | 回读完整输出快照并要求工具后续请求 |
| message.done / completed 携带完整文字 | 缺失的答案后缀被丢弃 | 按已交付前缀补齐，关闭后不再重复输出 |
| 空 HTTP body / 没有可识别输出 | 制造一个 finish | 明确 empty_stream 协议失败 |
| 5,000 个单字思考片段 | 5,000 次保留增量 | 复用 Chat 的 128 字符/40ms 合并边界，首片段立即交付，原文精确保留 |

生产修改为四个已有模块 openai-translate、glm-tool-continuation、responses-translate、responses-stream，以及三个职责单一的 Responses 装配辅助模块。两个新回归文件共 11 项测试。原有 WP20 黑盒夹具另有修正，见下节。没有新增依赖或持久化版本；新协议失败使用现有 error 事件，旧消费者继续按原合同处理。

## 红例、完整检查与暴露出的假阳性

隔离候选先通过未修改的完整 11 道门禁，测试条目数 4,293。随后将新增测试直接对冻结的未修复编译输出运行，11 项全部失败，原始 red.log 保留。修复后新增回归 11/11、供应商适配层 188/188 通过。探针同时证明两个 Chat 反例从“1 请求、无最终答复”变为“2 请求、执行一次工具、取得最终答复并携带原生续接”；Responses 未闭合数从 1 到 0，reasoning/cache 从 0 恢复到 40/80。

第一次完整修后检查保留为 verify-revealed-invalid-fixture.log：只有原有 WP20 Responses 目录测试失败。调查确认该夹具实际发出 Chat SSE，旧适配器因将无可识别输出当作完成而误过。本轮让 Responses arm 返回真正的 Responses SSE，并额外断言最终答案确实为 ok；没有放宽生产错误处理或删断言。五项对应黑盒测试全部通过。

最后重新运行原始 11 道门禁全部通过，耗时 379.95 秒；测试条目数 4,304，合同测试 38 项。门禁脚本、依赖锁文件及质量阈值均未修改。原始日志和此前失败一并归档。

## 火山真实连接验证

临时凭据仅在本次隔离进程中使用。普通 /api/v3 的具体模型请求返回 404 ModelNotOpen；Coding Plan /api/coding/v3/chat/completions 与 ark-code-latest 成功，响应实际模型为 deepseek-v4-1-flash。服务开通状态与 CLI 行为分开记录，不把普通入口拒绝当作产品失败，也没有修改全局供应商选择。

先用真实供应商适配器和 Loop 配合合成只读工具进行连续三次查询，修前已正确完成，已有思考内容进入下一次请求。修后同类验证再次完成；原生回传摘要校验 3 项，结果全部相同。这里的 profile/permission/tool 是隔离测试实现，不能冒充 Desktop 原生宿主证据。真实平台的正确回传要求参见[DeepSeek 思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)和[火山 Chat API](https://docs.volcengine.com/docs/ark/chat-api?lang=zh)；本轮没有盲目扩大模型/端点白名单。

再用 Desktop 固定 Node 启动真实 CLI，在新 Git 工作区实际读取 start.txt → step-b.txt → finish.txt。业务内容只含合成文件，默认思考强度保持未覆盖。修前、修后都读取恰好三次，最终 alfa bravo charlie 逐字正确，唯一终态 completed。修前单独样本 4875ms，首工具 2164ms；修后随附制品样本 5036ms，首工具 2259ms。它们验证正确性，不能构成普遍提速结论。与首轮完整测试同时运行的较慢修前样本（14,809ms、首工具12,458ms）保留，没有拿来计算收益。

本轮真实短任务没有复现“每次工具前都长思考”。11 项反例证明确定的本地协议缺陷已修复；不证明这些边界帧在用户原始长会话里出现过，也不能宣布全部长思考已解决。特别是 Responses 修复不能直接算成火山 Chat 路径的性能收益。

修后真实 Loop 的首个验证样本曾因验证器误拼“工具前说明 + 最终答复”而判 exactAnswer=false，三次工具执行和三项原生摘要均正确。该失败保留为 volcano-loop-after-all-text-oracle.json；验证器改为只核对最后一个 assistant_text，再次真实调用通过。没有修改生产答案或宽松匹配来制造通过。
