# 新旧 CLI 长思考差异与归因纠偏

状态：已归档（历史证据复算与当前源码核对；无产品修改）  
阶段：P08 Desktop 切换与 Parity  
最后更新：2026-10-23  
依赖决策：用户指出旧 CLI 同样没有思考档位入口，但使用中较少出现每次工具前长思考，要求重新审视解释。

后续修复：用户要求继续修复后，新增复现并修复了流式输出期间重复处理已保存历史的问题，且同步 Desktop 随附 CLI；见[施工与验证记录](2026-10-23-施工记录-流式思考期间重复处理历史修复.md)。以下保留归因调查当时的边界。

## 结论

思考档位接线是一个已完成的控制能力补充，不能据此解释新旧 CLI 的行为差异，也没有证据宣称这次接线已经解决长思考。此前把上游默认 max 放在解释首位，证据不足；这里修正该归因优先级。

现有证据支持优先调查实际请求与工具续接，而非继续盲调参数。已有一个保持 effort 省略的历史修复样本，观察到续接修复后推理及用时明显下降；但该缺陷已经修复，不能当成当前安装制品的已证实根因。目前没有完成当前制品、同协议、同模型、同任务的重复对照。

## 重新核对到的事实

### 1. 旧版无入口不等于内核不思考

当前旧版生产路径为 `trylo cli/src/QueryEngine.ts` → `src/query.ts` → `src/services/api/claude.ts`，不是无生产调用的 `utils/loopRunner.ts`。

`QueryEngine.ts` 未收到 ThinkingConfig 时按 `shouldEnableThinkingByDefault()` 选择 adaptive 或 disabled；`utils/thinking.ts` 在环境与设置没有显式关闭时返回 true。API builder 再根据 provider/model 能力选择是否发送 adaptive thinking 或 token budget。旧版内部还存在 effort 能力判断与配置解析。这里证明的是源码机制，不是旧日用请求的实际档位。

10 月 15 日旧版捕获器为避免记录思考正文，递归删除了名为 thinking 的字段，同时误删了请求的 thinking 配置。因此不能从历史捕获的字段缺省推断旧版关闭思考、低档运行或与新版完全相同。

### 2. 原生续接确实曾影响结果，且无需改变 effort

重新读取 10 月 15 日两个新版新鲜运行的安全数字归档：

| 指标 | 续接修复前 | 续接修复后 |
| --- | ---: | ---: |
| 显式 reasoning_effort | 省略 | 省略 |
| 工具数 | 35 | 35 |
| 模型请求次数 | 28 | 19 |
| 思考 token | 52,018 | 27,152 |
| 累计输出 token | 65,536 | 39,154 |
| 端到端用时 | 1,836.236 秒 | 914.943 秒 |

首个请求在仅归一化新工作区/home/session 身份后 body 相同，工具 schema 相同；候选仅叠加原生思考续接相关制品。修复后的 18 个后继请求共 154 条续接消息与此前接收内容长度及 SHA256 相同。

这是单个历史修复样本，支持执行框架续接会影响推理与任务推进，不能把时长变化全额归因、估计普遍提速比例或声称旧版必然更快。修复后功能检查通过，但说明文档仍有错误，严格完整自主交付依然未通过。

当前 `glm-continuation-checkpoint.ts` 已覆盖 Volcano Coding Chat 官方 endpoint 的 ark-code-latest、glm-latest、GLM 5.3/Flash 等名称，另有持久化和降级诊断机制；它并非所有服务商的通用续接。因此既不能继续报告这一旧缺陷普遍未修，也不能仅凭源代码存在就宣称用户实际安装版本已生效。

依据：[原始新旧长任务对照](../P00-工程地基与质量门禁/2026-10-15-实测记录-火山GLM53Flash新旧CLI长任务对照.md)、[续接定向修复与真实复测](../P00-工程地基与质量门禁/2026-10-15-定向修复-火山GLM工具思考续传.md)。

### 3. 不能简单归咎于新版提示词更长

复算同一历史首请求的捕获投影，单位是字符，不是 token。系统/消息大小由原捕获脚本对字段 JSON.stringify 后计数，包含包装和转义，不能当成精确纯文字长度：

| 项目 | 旧版 Messages | 新版 Chat |
| --- | ---: | ---: |
| 系统字段/消息序列化字符 | 15,934 | 8,158（四条 system 消息合计） |
| 工具数量 | 7 | 35 |
| 工具说明文字 | 23,748 | 9,853 |
| 工具 schema 紧凑 JSON 字符 | 6,525 | 12,698 |

旧版系统字段和工具说明更长，新版工具选择及 schema 更多。字符数量不能衡量模型的决策难度；数字不支持“新版提示更长所以更爱思考”的简单解释，不能排除具体规则、工具重叠或反馈形式影响模型。两种协议的系统/用户包装本来也不同，不能把它们当成有效的 prompt-only 实验。

当前新版 `agent-instructions.ts` 包含完整交付、逐项检查、验证和失败恢复要求，也有范围约束、复用已有事实、避免重复检查和完成后及时结束要求。没有每次工具前必须深度思考的显式规则，仍需单独替换提示词的真实对照才能判断这些要求的实际影响。

### 4. 工具开始时点不同，但不能解释全部长推理

旧版 API 在 `content_block_stop` 产出完整单块，query 在 streamingToolExecution gate 开启时交给 StreamingToolExecutor，可以在整段响应结束前启动已收齐的调用。gate 的历史生效值没有捕获，不能断言用户旧版每次都如此执行。

新版 `internal/loop/runner.ts` 在消费响应时实时发布文字与思考，但将工具留为一个批次，到 provider stream 完成后调度。这个设计可能增加“工具已经生成却还没开跑”的等待，需要用首个工具参数收齐→实际开始的时间测量。

它无法解释生成工具参数之前的全部实际推理。10 月 19 日一个历史请求服务端报告 27,354 reasoning tokens，首条思考约 4.339 秒到达、首次工具事件约 357.584 秒；不能把这些 token 全当作调度卡顿。旧版 Messages 历史用量没有 reasoning 子集，不能用零值推断不思考。

## 对照顺序与尚未证实部分

1. 先绑定当前实际运行制品、真实 endpoint、配置模型/响应模型、安全的生效参数与原生续接状态；源代码、开发资源包与已安装版本分开。
2. 两边统一协议、服务、显式档位及任务工程，用独立会话重复短任务：机械读取、局部改动、复杂排障。先排除服务端路径差异，再比较框架。旧 CLI 的 Messages 与新 CLI 的 Chat 不能直接算同条件。
3. 分别测请求→首思考、首思考→首个完整工具、完整工具→实际启动、工具结束→下次请求；同步核对真实结果。
4. 在能复现差异的条件下，依次独立改变原生续接、提示词、等价工具目录、工具反馈与上下文处理、调度时点。一次只改一个因素，质量验证和速度一起看。

当前有证据优先排查续接和请求语义，没有证据将剩余差异锁定为提示词、工具数量或调度单一根因。本轮没有新增真实 provider 调用或参数变更。
