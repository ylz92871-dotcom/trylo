## 1. 结论与边界

历史记录确有大量模型推理，不能仅归结为思考动画或用户主观感受。当前源码仍存在思考强度控制覆盖不完整的问题：终端可以显式传 Chat reasoning_effort，但 Desktop v1 不传；Responses 路径明确拒绝这个选项。未指定时交给上游默认，这并不等于自动低档。

如果实际后端是 GLM 5.3，官方默认恰好是 max，且不能关闭推理；5.3 Flash 的官方说明也给出同样的 low/high/max 与默认 max。因此“不主动设置 high”无法排除最高档运行。这是目前最值得做同模型、单因素验证的解释，不是已经测出的唯一根因。

已经存在的续接、图片传递、流式持久化修复应与当前控制缺口分开。当前源码不能证明用户上次使用的具体安装制品已包含这些修复；本次也没有新启动真实模型做前后 A/B。

## 3. 当前调用链逐项核对

| 项目 | 当前源码事实 | 对症状的含义 |
| --- | --- | --- |
| 默认执行提示词 | agent-instructions.ts 要求检查、交付和验证，也明确简单问题直接回答、复用已知结果、验证完成后及时结束；没有要求每次工具前深度思考 | 不能直接认定是提示词写了“必须长想”；复杂任务规则仍可能影响规划，需单独实验 |
| Chat 思考强度 | openai-compatible.ts:383 仅在显式配置时发送 reasoning_effort | 未传时使用服务端默认，客户端没有自动调低 |
| 终端选项 | args-run-options.ts / run-request-options.ts 支持 --reasoning-effort 并向 provider-build 传递 | 新 CLI 并非完全没有控制能力，但主要是运行参数通道 |
| Desktop v1 | trylo-v1-runner.ts:106 的入参和 argv 构建不传 reasoning effort | 用户无法通过这条启动链把思考档位传到 CLI |
| Responses | provider-build.ts:56 对非 Chat wire 拒绝显式 effort；responses.ts 仅配置公开 summary | reasoning summary 与计算强度不是同一个控制项；此路径尚未形成完整控制 |
| 工具开始时点 | runner.ts:415–516 先消费完整 provider stream，正文/思考实时发布，工具留到响应后统一调度；Chat translator 在 finish_reason 时闭合工具参数 | 模型生成了完整调用前不能执行，响应尾部也可能增加等待；不能预设成熟产品都能提前执行工具 |
| 工具批处理 | runner-effects.ts 已有按 parallelSafe 控制的并行批处理 | 不能把当前问题简单诊断成“所有工具都是串行执行” |
| 原生续接 | glm-continuation-checkpoint.ts:51 已识别官方 Volcano Coding Chat endpoint 下的 ark-code-latest、glm-latest 和 GLM 5.3 名称 | 早期别名绕过续接的缺陷不能继续当作当前未修事实；其他 endpoint 不自动拥有相同适配 |
| 通用 reasoning 回放 | transcript-messages.ts 不把展示推理回放为普通消息，原生续接由 provider adapter 拥有 | 不能为了“记住思考”直接把展示正文粘回系统提示词 |
| 上下文增长 | 历史一个会话输入从 15,717 增到 48,142 token，并有 cacheReadTokens | 上下文是可能影响因素；没有成分拆分和因果实验，不能断言是工具表、规则或压缩单独造成 |

## 5. 与成熟产品比较

本节比较公开机制，没有做跨产品速度排名。不同模型、上游、任务、缓存和思考强度的使用感不能直接等价为 CLI 内核差距。

| 对照产品 | 官方可核对机制 | Trylo 当前差距或应保留部分 |
| --- | --- | --- |
| Codex | model_reasoning_effort 与 model_reasoning_summary 分别控制计算强度与展示摘要；可用档位随模型变化 | Trylo 不应把“显示多少思考”当成“模型算多久”；补全 Desktop 与 Responses 的真实强度通道 |
| Claude Code | 支持模型的 effort 可选择，adaptive reasoning 按步骤复杂度决定思考；默认也可能较高，并非永远轻量 | 重点是模型能力感知、显式选择和当前生效值；不能声称成熟产品每步都不思考 |
| OpenCode | 按模型能力元数据生成 variants，分别支持 effort、开关或 token budget；provider/model/variant 可逐层覆盖 | Trylo 目前单个 Chat 参数不足以表达多 provider 的支持范围，需要明确拒绝不支持的组合 |

官方依据，均在本次打开核对：

- [Codex 配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)：effort 与 summary 是不同设置。
- [OpenAI reasoning 指南](https://developers.openai.com/api/docs/guides/reasoning)：较低 effort 偏向速度和较少 token，较高 effort 为复杂任务提供更多推理；原生 reasoning continuity 按协议保留。
- [Claude Code 模型配置](https://code.claude.com/docs/en/model-config#adjust-effort-level)：effort、adaptive reasoning、模型相关默认值与会话选择。
- [OpenCode 模型与 variants](https://opencode.ai/v2/docs/models#variants)：能力元数据、effort 与 budget 区分以及配置覆盖。
- [GLM 5.3 官方说明](https://docs.z.ai/guides/llm/glm-5.3#feature-changes)：强制推理，low/high/max，默认 max。
- [GLM 官方仓库](https://github.com/zai-org/GLM-5/blob/main/README.md)：5.3 / 5.3 Flash 的档位与默认值。
- [GLM 思考模式](https://docs.z.ai/guides/capabilities/thinking-mode)：工具之间可以继续思考，原生思考续接需按接口合同保留。

## 6. 建议后续顺序

1. 先绑定用户实际 Desktop/CLI 制品、请求 endpoint、配置模型、响应实际模型与请求 effort；别名和未传档位必须如实标记，不能把未传写成“低”或“自适应”。只保存安全元数据。
2. 对同一真实模型做隔离的单因素对照：先比较当前默认与显式 high，再按模型能力比较 low。保持任务、初始工程、其他提示词与工具表一致，使用独立 home/session，不改全局选择。模型别名需记录响应身份与时间，不能假定控制台别名永远固定。
3. 分开记录 api_call、首思考、首工具参数、工具实际开始、权限等待、工具完成与首正文；以多次样本的中位数和尾部延迟看机械读取、局部修改、复杂排障。质量按真实结果核对，不能用 completed 或更短时间替代。
4. 依据对照结果补全 Desktop 与各 wire 的能力感知档位控制，再决定默认策略。GLM 5.3 不能用 none 作为通用提速办法；其他模型也需要验证调用工具与结果正确性。
5. 提示词精简、进一步存储优化或提前执行工具都作为独立因素。先证实收益，避免同时改档位、规则、上下文与调度后失去归因能力。

本次完成的是代码调用链核对、历史真实数字复算和官方机制比较。没有修改产品源码、构建目录、全局配置或原始会话，没有运行新的付费 provider 请求，没有宣称已经改善当前安装版本的延迟。
