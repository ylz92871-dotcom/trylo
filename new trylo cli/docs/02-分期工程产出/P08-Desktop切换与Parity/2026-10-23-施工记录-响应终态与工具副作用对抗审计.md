状态：修复、完整门禁和随附 CLI 制品验证完成  
阶段：P08 Desktop 切换与 Parity  
日期：2026-10-23  
依据：用户要求从不同角度继续对抗审计、找到问题并修复；使用仓库 trylo-code-quality，隔离基线并保留原始失败和并行修改。

## 已证实的问题

本轮从响应可信度、审批顺序、实际文件效果、工具身份一致性、答案一致性和恢复六个角度推进。它们是明确的正确性缺陷，不能直接折算为思考 token 或认定全部长思考均由此引起。

1. 核心循环虽然等流读取结束后才执行工具，却按输入顺序先处理工具请求、后处理错误。一个完整工具调用后出现断流、失败或取消，仍可能先请求审批并执行工具。Chat 和 Responses 都受影响；输出长度截断、内容过滤和未知结束原因也不能保证工具被阻止。
2. Responses 适配器在未收到终态事件的 EOF 上制造 finish；外层把它当作响应完成，执行工具并继续请求模型。
3. response.completed 内部的 cancelled、queued、in_progress 和未知状态被折叠为 stop。取消、未完成工作因此可能报告 completed。
4. Responses 同一 item_id 或 call_id 的不同完整参数快照被静默去重，第一份参数可能执行，后面的冲突被忽略。
5. 正文快照若撤回已流出的文字会被静默忽略；消息封闭后又丢失已交付正文，最终快照的不同金额等冲突也被忽略。

修前 21 个定向场景中，18 个异常场景失败，3 个正常/兼容控制通过。异常场景还覆盖多工具批次和恢复后不重执行。随后用 Desktop 随附的固定 Node 和真实 CLI 子进程、真实 HTTP SSE、本地临时 write_file 与 stdio 审批验证：7 种异常都发起审批并在批准后真的写入文件，断流、取消和参数冲突三种还报完成。两个正常控制完成审批、写入和后续回答。模型响应为本地合成，不能称为外部真实服务或原生 UI 验收。

## 修复合同与兼容

Loop 的 stream-verdict 只依赖规范 ReduceInput，是响应是否可以授权工具的唯一判断：必须有 stop/tool_calls 成功结束，且没有 transport_fail、transport_unknown 或 cancel。未经认可的响应保留文字、用量和明确终态，但过滤工具请求、打开参数块及无效参数执行接点，不发起工具审批，不执行工具，不因 requiresFollowUp 追加请求。长度截断仍进入原有 output_tokens_exhausted 合同。providerFinished 也只接受成功原因，内容过滤和未知原因不能直接完成回合。

Responses EOF 现在报告不可重试的 protocol 错误，不生成成功结束；重复 complete 静默。显式取消生成 cancel_ack；已知失败和长度截断保留既有语义。为兼容稀疏网关，response.completed 缺少 status 仍可接受；显式的非终态或未知值会拒绝。依据是 [OpenAI 官方 Responses 事件合同](https://developers.openai.com/api/reference/resources/responses/streaming-events)：completed、failed 和 incomplete 是不同事件；output_item.done 是单个输出项结束，不是整条响应的成功凭据。

工具装配器按 item_id 和 call_id 保存已结算的名称及规范参数身份，使用现有 stableJson 对 JSON 语义去重。相同快照、属性顺序不同的同义参数和缺少参数的重复快照仍静默且只结算一次，显式矛盾则报告 protocol 错误。流式片段与第一次完整快照的既有“完整快照补齐”合同保留。正文装配器保存封闭块的正文用于核对，允许开放块补齐后缀，拒绝撤回和封闭后的矛盾快照。适配器一旦报错就封闭，不再补一个成功 finish。

没有修改 CLI v1 事件结构、持久化格式、权限所有者、学习审批、依赖或全局供应商选择。成功路径仍只有一个工具执行入口，权限判断仍由现有 Permission Service 执行；供应商实现未进入核心。严格终态处理可能让过去静默成功的损坏网关响应明确失败，这是有意修正，不通过猜测补出成功。此前已错误执行的外部效果无法由该修复追溯撤销。

## 验证与夹具纠错

冻结修前完整 11 项门禁通过，4341 个测试条目。修后 21 个定向场景以及相关权限、工具和磁盘恢复测试合计 61 项通过。

初次定向检查保留了一条旧测试失败：它要求没有完成帧也产生 finish，现改为断流协议失败、无 finish、重复结束静默。完整检查又暴露 12 处工具测试夹具（影响 16 项测试）没有提供正常结束事件，却要求执行工具。其中 11 处检查审批/输出/未知结果，另一处是制造工具执行结果未知的磁盘会话共享夹具。已补上成功 tool_calls 终态，原有审批拒绝、取消、权限所有权、输出截断、未知结果阻断、人工核对及恢复不重复执行断言全部保留。原始断流测试及新增反例没有改成正常结束，没有修改门禁脚本或阈值。两轮完整失败日志保留，不能跳过或称为已通过。

编译准备曾因工作目录下相对路径错误未执行更新；后续冻结源文件并重新构建，最终完整门禁独立清理和构建 dist，未采用那次准备结果作为验收。没有终止用户进程。

最终原始 11 项门禁全部通过，4362 个测试条目、38 项合同检查，耗时 442.11 秒。更新后随附制品的同一组 21 项回归全部通过。7 个生产模块的 JS/声明各 14 个输出分别同步到开发 dist 和 Desktop 资源，共 28 份 hash 绑定；源码与冻结候选一致，2822 项新资源清单完整核对。仅覆盖本轮输出，原始输出和清单保留，未提交 Git 或更新安装包。

同一固定 Node/随附入口的 9 个真实 HTTP、进程和文件实验全部满足预期：7 个异常均只有一次模型请求，零审批、零文件效果；取消明确为 cancelled，其他故障保持 unknown/failed，长度截断保留预算失败。两个正常控制各审批一次，审批前文件不存在，随后实际写入精确内容，并在第二次请求后给出 VERIFIED。不能把本地合成响应称为真实供应商输出。

真实火山实验使用用户为本次授权的临时凭据，Coding Plan 的 ark-code-latest，实际响应模型 deepseek-v4-1-flash，未指定思考档位；只生成合成工作区及未知随机校验串，限制请求数与输出额度。共 3 个 HTTP 200 请求：负向实验保留真实工具参数并人为去掉 finish_reason，形成可控终态丢失；只有一次请求，CLI 终态 unknown，没有工具执行。正常实验实际读取一次，两个请求后 completed，返回与物理文件完全一致的未知校验串。它验证真实模型输出通过本轮门禁的正常/受损终态边界，不是自然网络故障、用户原始长会话或思考耗时改善的证明。

真实实验初次因脚本未提供 stdio 用户帧而被 CLI 在请求前拒绝，未调用 API，原目录和日志保留。第二次两组真实 CLI 输出已满足目标，但脚本错误期待只读 read_file 产生一次审批，导致汇总进程断言失败。现有 binding 是无需审批的只读工具；依据现有权限合同修正 oracle 后，独立重新核验不可变的 CLI 输出、物理文件和 wire 摘要，两组通过，没有为改测试重复调用供应商，也没有把原始汇总进程的失败改写成退出 0。带真实副作用的审批顺序仍由 write_file 进程实验单独证明。158 个任务脚本、日志和隔离会话文件的临时凭据扫描为零命中；密钥未放入参数、源码、配置或公开证据。

## 自审、风险与回滚

作者按可读性和维护性、架构、正确性、权限、并发恢复、性能、依赖顺序自审：核心门禁是独立纯函数，供应商事件仍由适配器拥有；错误词汇统一由 Responses helper 构造；参数规范化复用现有唯一实现。封闭正文仅在当前流内保留一份引用，工具快照在结算时核对，不增加逐 token 全历史扫描。没有新增依赖或扩大授权。此为作者自审及执行证据，不称独立审计。

兼容边界是“明确成功才执行工具”，不是识别所有未来供应商协议。真实服务的模型遵循、完整长会话表现、原生 Desktop/WebView2 与安装包仍需对应证据。当前开发资源更新也不代表已运行的旧进程自动加载了新字节。

原始文件、冻结候选、失败日志和进程工作区保存在 work/thinking-adversarial-20261023-r3；publish-before 保存本轮覆盖的旧输出及清单。回滚先核对 after hash，再反向应用本轮源代码差异并恢复本轮输出和清单，保留所有并行及后续修改，不能整树覆盖。
